## 1. Project Context

- **Framework:** Expo SDK 54 + Expo Router 6 (file-based routes in `app/`)
- **Backend:** **Supabase** (existing project; not yet wired into this mobile repo)
- **Server state:** **TanStack Query** over Supabase client (feature-scoped keys; no ad-hoc fetch-in-screen pattern)
- **Client state:** Context for auth session only; feature-local `useState` for forms/wizards (no Redux/Zustand until a real need appears)
- **Routing model:** File-based Expo Router (`app/`); route files stay thin and compose feature screens
- **Styling:** NativeWind v4 + React Native Reusables (`components/ui`) + CVA
- **Test runner:** None yet → target Vitest (unit) + Maestro or Detox later (not blocking v1)
- **Current shape:** **Greenfield** — RNR minimal template (`app/`, `components/ui`, `lib/`); no product features yet; no `supabase` package in this repo yet
- **Source of feature names:** Product brief (university clinic booking for students/professors); not from existing routes

**Rules applied:** project context anchors every later decision; no rule
is cited here because this section is informational.

**How `via app` works in practice:**

- Booking needs slots → `app/(student)/book/index.tsx` calls `useAvailableSlots()` and passes `slots` into `BookingWizardScreen`.

## 6. State & Data Ownership

| Feature | Server state owned | Client state owned | Shared state consumed |
|---------|--------------------|--------------------|------------------------|
| `auth` | session / current user | login form fields | — (auth **is** the shared identity source via app composition) |
| `booking` | create booking mutation | wizard draft (service, date, slot) | `userId`, `role` via props from app |
| `appointment` | list / detail / cancel | filters (upcoming vs past) | `userId` via props |
| `schedule` | available slots by day/service | selected day in picker UI | clinic/service id via props |
| `profile` | profile record | edit-form draft (later) | `userId` via props |

- **Server state library (target):** TanStack Query. Keys are feature-scoped:
  - `['auth', 'session']`
  - `['booking', 'draft', userId]`
  - `['appointment', 'list', userId]`
  - `['appointment', 'detail', id]`
  - `['schedule', 'slots', serviceId, date]`
  - `['profile', userId]`
- **Client state:** no global store for booking draft across unrelated trees; keep wizard state inside `booking` and reset on unmount.

**Data access:** Feature `api/` modules call Supabase (via `shared/lib` client). Use thin mocks only if offline UI work must proceed before credentials are in this repo — same function signatures either way.

**Rules applied:** `fstate-feature-scoped-stores`, `fstate-server-state-separation`, `fquery-colocate-with-feature`, `fquery-feature-scoped-keys`, `fstate-reset-on-unmount`.

## 7. Cross-Feature Communication Policy

**Chosen mechanism:** Composition at the app layer only (default).

**Rationale:** CampusCare v1 has a clear parent flow (auth → book → appointments). Expo Router layouts/screens are the natural composers. An event bus or shared Zustand slice would add complexity before we have a backend.

**Examples:**

- **Book needs slots** — route loads `useAvailableSlots()`, passes `slots` + `onSelectSlot` into booking UI.
- **After confirm** — route calls booking mutation, then `router.replace` to `/(student)/appointments/[id]`.
- **Role home** — `app/index.tsx` reads `useSession()`, redirects to `(student)` or `(professor)` or `(auth)/login`.
- **Professor vs student** — **same booking capability**; route groups may share screens via composition. Do not fork features by role.

**Rules applied:** `bound-event-based-communication`, `fcomp-composition-over-props`, `fcomp-props-as-data-boundary`, `bound-feature-scoped-routing`.

## 8.1 Security & Data Integrity Standard (panel-ready)

**Boss decision:** Mobile is a **scheduling client**, not an EHR. That is the strongest integrity posture for a student thesis panel without overbuilding.

### What the mobile app may store / show
- Campus identity linkage (`user_id`, role, display name, student/employee id if required)
- Service / visit **type** (e.g. general consult, dental screening) — categorical, not free-text diagnosis
- Slot datetime, clinic location label, booking status (`pending` \| `confirmed` \| `cancelled` \| `completed`)
- Cancellation reason as **optional enum**, not clinical narrative

### What must NOT live in this mobile app or its tables (v1)
- Diagnoses, prescriptions, clinical notes, attachments of medical images, lab results
- Staff-only operational data (belongs in web repo)

### Supabase hard rules (non-negotiable)
1. **RLS on every** `public` table from day one. No “open table then lock later.”
2. **Role for authorization** lives in `app_metadata` (or a `profiles.role` column enforced by trigger) — **never** trust `user_metadata` for RLS.
3. Mobile ships **only** the anon/publishable key. **Never** `service_role` in Expo.
4. Policies: users **select/insert/update** only rows where `user_id = auth.uid()` for their bookings/appointments; schedule/slots are read for `authenticated`; writes to slots are **not** granted to mobile roles (staff web / service role only).
5. Prefer **DB constraints** for integrity: FKs, `CHECK` on status/role, unique `(user_id, slot_id)` to prevent double-book, `NOT NULL` on required booking fields, `updated_at` triggers.
6. Soft-cancel (`status = cancelled`) rather than hard-delete of appointment history (auditability).
7. Short-lived sessions; sign-out clears local session; no secrets in AsyncStorage beyond Supabase session handling.
8. Before any panel demo: run Supabase security advisors / RLS review on booking-related tables.

### Integrity story you can tell panelists
> “Students and professors book and manage their own appointments. Clinical records stay on the staff web system. The database enforces who can read or write each row (RLS), roles are server-controlled, and bookings can’t collide on the same slot.”

**Rules applied:** Supabase security checklist (RLS, app_metadata, key exposure); least privilege; separation of mobile vs staff surfaces.

## 10. Conformance Checklist (human review)

### Structure

- [ ] Business logic lives under `features/`, not in `app/` route files beyond composition.
- [ ] `shared/` has no clinic-domain components (`AppointmentCard` belongs in `appointment`).
- [ ] `app/` route files mostly import from `@/features/*` and `@/shared/*`.
- [ ] Every feature has an `index.ts` public API.
- [ ] Feature folders stay flat (no deep nesting beyond `api|components|hooks|types|utils`).

### Imports

- [ ] No `features/A` imports `features/B` internals or public API unless matrix says `allowed` (default: never).
- [ ] `shared/` never imports from `features/` or `app/`.
- [ ] Features never import from `app/`.
- [ ] Cross-feature data passes through route props / layout composition.

### Boundaries

- [ ] Student vs professor differences live in `app/(student)` vs `app/(professor)`, not duplicated feature forks.
- [ ] Booking does not call appointment APIs directly.

### Data and state

- [ ] Query keys start with feature name.
- [ ] No mirroring of server lists into global stores.
- [ ] Booking wizard state resets when leaving the flow.

### Naming

- [ ] Feature folders are singular domain nouns: `auth`, `booking`, `appointment`, `schedule`, `profile`.
- [ ] Exports are descriptive (`AppointmentCard`, not `Card`).
